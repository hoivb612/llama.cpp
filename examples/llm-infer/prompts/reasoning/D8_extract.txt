# D8 ENSEMBLE - generative EXTRACTION stage.
#
# This file is deliberately NOT a classifier prompt. The model's job is to pull
# structured facts out of the utterance; the classification is done afterwards
# in code (see examples/llm-infer/laya/d8_ensemble.py).
#
# Derived from reasoning/D8.txt. The ONLY change is the required JSON schema:
# the original asked for {answer, justification} -- answer FIRST, which in an
# autoregressive model means the verdict is emitted before any reasoning token
# exists. The justification is then causally downstream of the decision and
# cannot inform it, which is why the original confabulates ("correctly
# identified the phone number for 'Josie'" about Sophie's 849456).
#
# Measured on Gemma-4-E4B-it Q4_K_M, 8 threads, 40 utterances:
#
#   variant                      score    a/b/c/d digit classes
#   reasoning/D8.txt (orig)      27.8%    10/26   answer-first, no scratchpad
#   justification-first only     33.3%    12/26   unstable: 16/40 unparseable
#   this file, model's `answer`  61.1%    22/26
#   this file, code-mapped       72.2%    26/26   <-- take the FIELDS, not the answer
#
# The jump from 61.1 to 72.2 costs nothing: it is the same run, re-scored by
# ignoring the model's own `answer` and mapping `player_number` through the
# phonebook in code. The model extracts digits correctly on 36/40 utterances
# (every labeled one) but only agrees with the table on 30/40 -- it is a
# reliable reader and an unreliable look-er-upper. Let it read; look up in code.
#
# A `proposes_other_person` field was tried here and REMOVED: it caught 8/10
# deflections but produced 12/30 false positives, a net loss. Deflection ('z')
# is supplied instead by the Laya guard battery in
# prompts/reasoning_laya/laya_D8_guarded.txt, which gets 6/10 at zero false
# positives because its thresholds sit under a measured FP floor. Detection and
# calibration are different capabilities.
#
# ---------------------------------------------------------------------------
# WHY THE ROUTING GOES THIS WAY (read before changing the split)
#
# The intuitive assumption is that the scorer handles the mechanical classes
# and the generative model handles the ones needing understanding. D8 measures
# the exact opposite:
#
#   subtask              nature     decision model      SLM (E4B)
#   z deflections        SEMANTIC   6/10 at 0 FP        0/10
#   a/b/c/d digits       SYMBOLIC   no usable signal    26/26
#   Mara, 18 utterances  SEMANTIC   18/18               --
#
# D8 is built to force that distinction. Rows 16-30 ('c') and rows 31-40 ('z')
# reuse the SAME phone numbers -- row 26 "Is Josie's number 960564?" and row 31
# "Why don't we ring Nicky B? His number is 960564" are identical on digits and
# opposite on label. Nothing but meaning separates them, and that is the class
# the scorer gets and the SLM misses completely.
#
# The converse was tested directly and is not a wording problem. See
# prompts/reasoning_laya/laya_D8_spelled.txt: eight probes asking about digit
# content in spelled-out form ("ends in eighty-four") produced a best margin of
# -0.107, every probe peaked on class 'a' regardless of what it asked about,
# and cross-probe correlation averaged r=0.806. The probes were not reading
# digits; they were all reading one shared utterance-level factor. The encoder
# does not represent digit identity in any direction the scoring head can read.
#
# Generalisation to carry forward as the model family evolves:
#   scorers    - strong on holistic utterance-level gist (intent, stance,
#                deflection, tone). Weak-to-absent on compositional symbol
#                work (compare two strings, index a table, carry a value).
#   SLMs       - strong on extraction, copying and sequential symbol
#                manipulation. Weak on producing a CALIBRATED single-shot
#                judgement; they detect well and threshold badly.
#
# So: symbols -> generative, gist -> scorer, decision -> code. Routed the other
# way round the ensemble scores WORSE than either model alone.
#
# When a new decision model arrives, re-measure this split before trusting it
# -- analyze_probes.py reports the margin per (probe, class); a negative margin
# means no threshold exists at any wording, which is the signal to move that
# subtask out of the scorer entirely rather than keep tuning prompts.
# ---------------------------------------------------------------------------
#
# Do not "tidy" the schema. These numbers are for this exact wording.
